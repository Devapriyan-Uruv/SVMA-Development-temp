# V5 final control note — 11 Sep 2026

This file contains historical implementation notes from earlier rounds. The final V5 behavior supersedes any earlier note that said a target-less reading may still be saved. In V5, **no active Quality/Solvent/Boiler data-entry parameter may operate without a visible approved target**. Existing source rows with a blank target are retained in the parameter master for audit/configuration but are made inactive. The operator UI also defensively locks any legacy target-less row, the API returns `TARGET_REQUIRED`, and deviation classification is impossible without a target. Historical readings are not deleted. See `RELEASE_V5_FINAL.md` and `SQL_EXECUTION_ORDER_V5.md` for the final deployment contract.

# Implementation Notes — V3 Operational Intelligence

This round is a **backend/operational** pass on top of the already-redesigned V2.5 codebase. No Behance/visual redesign work was repeated — `app/globals.css`'s existing layers (V1–V7 now) are additive-only, and no page was restyled. This document records what already existed before this round, what was actually built, and the judgment calls made along the way, so a reviewer doesn't have to reconstruct them from the diff.

## 1. What already existed (confirmed by direct inspection before writing anything)

- `sql/001_schema.sql`, `005_v2_parameter_expansion.sql`, `009_v2_4_product_intelligence.sql` — a comprehensive schema: `parameter_master`, `parameter_entries`, `deviations`, `deviation_tickets`, `notifications`, `notification_preferences`, `shift_sessions`, `audit_logs`, RLS on every table. This is why the brief's instruction — "do not rebuild it from scratch" — was followed literally: V3 **extends** this schema (new columns, two new tables) rather than replacing any of it.
- `sql/005_v2_parameter_expansion.sql` already imports essentially every Solvent/Safety/Boiler parameter present in `DocScanner 5 Sept 2026 606am 1.pdf` pages 1–21 (Ground Floor, Hexane Tank, DT, Cooling Pond, Extractor, Second Floor, Preparatory, Raw Material Godown, Packing Godown, Palvarizer Godown, Factory General Safety, Vision Boiler, CVL Boiler). No new Solvent parameter import was needed this round.
- `app/api/reports/route.ts` (fixed in round 4) — confirmed AI already runs after, not instead of, the deterministic report, and is not on the save path. No change was needed here for Section N/AJ; it was already spec-compliant.
- The `notifications` table, its RLS (`notifications_self`), and a first version of the topbar bell (round 4) already existed — V3 adds Realtime, sound/vibration, acknowledgement and de-duplication on top of that foundation rather than building notifications from zero.

## 2. Two confirmed production bugs, root-caused and fixed

**Bug 1 — previous-hour entries were editable.** `app/api/entries/route.ts` POST used a plain `.upsert(payload,{onConflict:'shift_session_id,parameter_id,slot_start,product_code'})` with no `ignoreDuplicates`. Postgres `upsert` without that flag is `INSERT ... ON CONFLICT DO UPDATE` — so a resubmitted slot silently overwrote the original captured value. There was no server-side lock at all; only the UI happened to stop rendering old rows as editable in some views.

**Bug 2 — a missing target was silently treated as Normal.** The old status mapping collapsed `unconfigured` (no target configured) into DB status `'normal'`, and the notification block only fired `if(v.severity && param.alert_enabled)` — which is false when there's no target, so severity is `null`. A reading against an unconfigured target produced no visible signal anywhere.

Both are fixed at the root (see `ENTRY_IMMUTABILITY.md` and `NOTIFICATION_FLOW.md` for the mechanisms), with DB-level enforcement in addition to the API fix, so the bug class cannot resurface through a future code change to the route alone.

## 3. New capability, in one paragraph each

- **Immutable entries + amendment workflow** (`entry_amendments` table, `enforce_entry_immutability()` trigger, `POST/GET /api/entries/amend`). A submitted reading can never be overwritten — not even by a service-role UPDATE — except through the audited amendment path, restricted to Solvent Head / Quality Head / Super Admin, matched to the entry's module.
- **TARGET_MISSING as a first-class status** (`entry_status` enum value, `dbStatus()` mapping, dedicated notification branch in `app/api/entries/route.ts`). The reading still saves; Dept Head, CEO and Super Admin are notified immediately; the dashboard counts it separately from Normal/Warning/Critical.
- **Deterministic target parsing extended** (`lib/targetParser.ts`) to understand the new Quality workbook's plain-English directional wording (BELOW/MAX/UPTO/ABOVE/MIN/etc.), while explicitly refusing to guess at genuinely ambiguous multi-branch text (see `QUALITY_MAPPING.md`).
- **Real-time, audible, acknowledgement-gated alerts** (`lib/alerts.ts`, `components/NotificationBell.tsx`, Supabase Realtime). Critical alerts stay on screen until explicitly acknowledged; the sound is gated behind a one-time browser-gesture unlock control, as required by browser autoplay policy.
- **Configurable ticket severity threshold** (`parameter_master.ticket_severity_threshold`) instead of hardcoding "only Critical opens a ticket" — see the judgment call in §4.
- **Quality sample/result SLA tracking** (`quality_sample_tasks` table, task generation on shift-session open/product-change, `PATCH /api/quality/sample-tasks` to mark received, `GET /api/quality/sla-sweep` for overdue detection, auto-linkage from a submitted result back to its task in `app/api/entries/route.ts`). See `QUALITY_MAPPING.md` for exactly how sample-due and result-due timestamps are computed from the workbook's free text.
- **Full Quality parameter re-import from the actual attached workbook** (`sql/011_v3_quality_full_import.sql`, 79 rows), superseding the hand-typed partial list in `009_v2_4_product_intelligence.sql` rather than layering on top of it. See `QUALITY_MAPPING.md`.
- **Dashboard filters** (Date, Date range, Product, Severity — plus Shift on Solvent) added to `app/api/solvent/dashboard/route.ts`, `app/api/quality/dashboard/route.ts` and their analytics pages, all applied server-side against the same query so KPIs/charts/timeline move together (Section AF).
- **Admin configuration** for the two new per-parameter knobs (`ticket_severity_threshold`, `sample_grace_minutes`) added to the existing Parameters admin drawer — no new screen.

## 4. Judgment calls made without stopping to ask (per the brief's explicit "implement end-to-end, don't ask per screen" instruction)

- **Full re-derivation instead of patching `009` row-by-row.** `009`'s hand-typed Quality list (87 rows) already had the product/group structure substantially right — including a correct `EDIBLE COPRA CAKE` / `NON-EDIBLE COPRA CAKE` split, which direct inspection confirms is a real, literal column-A value in the workbook (row 4 alone reads `EDIBLE COPRA CAKE`; row 5 starts a new literal group `NON-EDIBLE COPRA CAKE` that forward-fills through rows 5–8) — but it left **target_text null for roughly half its rows**, and a handful of the numeric ranges it does carry differ from the currently-attached workbook (e.g. DORB `% MOISTURE` is `11-12` in `009` vs `10.5% - 11.5%` in the attached sheet; `% FIBER`/`% PROTEIN` similarly shifted). Rather than diff and patch `009` row-by-row against text whose provenance can't be confirmed, this round re-derived the full 79-row list **directly and only** from the attached `LAB REPORTS AI 1.xlsx`, preserving the workbook's literal text — including apparent source quirks such as `PALM KERNAL CAKE` (not the corrected spelling `PALM KERNEL CAKE` `009` used) and `NICE- 1` without a space (vs `009`'s `NICE - 1`) — and flagging rather than guessing at genuinely ambiguous cells (`OOS`, multi-branch E/NE splits like `E - B 5 % & NE -AB.-10 %`) as `source_review_required=true`, which `009` either left null or silently guessed a value for. `011` deactivates all of `009`'s Quality `PROCESS LAB REPORT` rows before inserting the freshly-derived set, so there are never two competing parameter definitions live at once. See `QUALITY_MAPPING.md` §3 for the full row-level comparison.
- **Ticket-severity threshold.** The brief's own acceptance tests imply a ticket should sometimes be created for a Warning, not only a Critical, deviation — but the original code only ever created a ticket on Critical. Rather than silently picking one interpretation, this was made Super-Admin-configurable per parameter (`ticket_severity_threshold`, default `'warning'` — i.e. both Warning and Critical open a ticket unless narrowed), consistent with Section AL ("ticket rules are configurable") and Section I/J ("AI/code never decides severity policy for the business").
- **Dashboard filter scope.** The CEO page itself was left as-is (it already aggregates both modules); the new Date/Date-range/Product/Severity filter row was added to `solvent/analytics` and `quality/analytics`, which is where a Dept Head actually drills into a specific slice. A full filter bar on every page was judged lower-value than getting the core operational-integrity fixes (immutability, TARGET_MISSING, SLA) fully done and verified within the available time.
- **PDF pages 22–30 (Thermic Fluid Boiler, Softener, RO, ETP, Workshop, Refinery Plant Safety Checklist).** These were read in full but not individually cross-checked line-by-line against `sql/005_v2_parameter_expansion.sql`'s existing Boiler/Safety sections. The existing sections already cover the large majority of this content (Vision Boiler, CVL Boiler, Factory General Safety are already imported). This is a known, minor gap — flagged here explicitly rather than silently — and is the one piece of the source material that should get a follow-up pass before being treated as fully verified.
- **`entry_amendments` requester/approver names.** `GET /api/entries/amend` returns raw `requested_by`/`approved_by` UUIDs rather than joined profile names, because a double self-join to `profiles` for the same table depends on guessed Postgrest-generated FK constraint names, which is a real runtime-error risk. The UI resolves names client-side from the already-loaded roster instead. Documented here as a deliberate simplification, not an oversight.

## 6. Round 6 / V4 — QC data-entry realignment from the three PDF lab reports, scoped strictly to the existing Quality module

You supplied three new source documents (`PK_LAB_REPORTS.pdf`, `COPRA_LAB_REPORTS.pdf`, `RB__LAB_REPORTS.pdf`) and asked for the code to be modified "only for the existing QC data entry according to the new file logic," with the UI redesigned "like a UI/UX developer for all the modules." Read as a solution architect first, this split into two separable pieces of work, executed in that order:

**Scope decision, made explicit up front.** "The existing QC data entry" is the Quality module's parameter data end-to-end — the parameter definitions (`parameter_master`), the entry screens, the Quality dashboard/analytics, and Quality's slice of the Admin parameter config. It does **not** include Solvent or Finance, and no file under `app/solvent/**`, `app/finance/**`, `app/api/reconcile/**`, or the three finance-logic `lib/` files was opened this round — verified both by scope discipline while working and by the hash re-check in `FINANCE_LOGIC_VERIFICATION.md`.

**Data layer — new parameter set, not a patched one.** The three PDFs supersede `011`'s xlsx-derived Quality parameters the same way `011` superseded `009`'s hand-typed list: full re-derivation directly from the newly-attached source, not a row-by-row diff-and-patch. See `QUALITY_MAPPING.md` §8 for the complete accounting — 83 rows (PK 32 / COPRA 32 / RB 19), 20 flagged `source_review_required` for a human to confirm (bare numbers with no stated direction; the `FLASH POINT ... NIL` compound criterion present in all three products), applied via the same deactivate-then-upsert non-destructive migration pattern (`sql/012_v4_quality_report_realign.sql`) that preserves every historical `parameter_entries` row. **Zero changes to `lib/targetParser.ts` or `lib/slaParser.ts`** — every pattern in the three PDFs (ranges, `<`/`>` symbols, "EVERY-2 hrs.", "3 mts.", "8 hrs", etc.) was checked directly against the existing parser logic before a single row was transcribed, and all of it was already tolerated.

**UI/UX — "redesign for all the modules," read as the Quality-module screens this round's data change actually touches, not a full-app visual pass.** `UI_REDESIGN_NOTES.md`'s prior four rounds already did a full-app visual redesign (typography, color, spacing, the drawer/modal system) — re-running that here on unrelated Solvent/Finance/Admin screens would be outside this round's own scope instruction. What was redesigned, and why each piece earns the description "the UI, for the modules this data-entry realignment actually touches":
- **The Quality hourly entry screen** (`components/ParameterEntryBoard.tsx`, quality-scope grid mode) — rebuilt from the shared single-hour Solvent-style table into a grid that mirrors the paper lab-report form: all 8 hour columns visible per parameter row at once, plus live MIN/MAX/AVG and a Comments column, so an operator sees the whole shift's trend for a parameter without switching hours. Only the currently-selected hour's column is ever editable — the existing one-hour-per-save contract, entry immutability, and 409 ENTRY_LOCKED amendment-only correction flow are all unchanged; this is a rendering change, not a data-model or validation change. See `UI_REDESIGN_NOTES.md`'s new round for the full rationale on why editability stayed hour-scoped.
- **Quality dashboard and analytics** (`app/api/quality/dashboard/route.ts`, `app/quality/analytics/page.tsx`) — MIN/MAX added alongside the existing AVG, computed client-request-time from already-loaded shift readings (pure arithmetic, nothing stored), mirroring the paper form's own trailing MIN/MAX/AVG columns.
- **Admin → Parameters** — a real, pre-existing gap closed as part of this instruction: `parameter_master.source_review_required` has existed in the schema since `001_schema.sql`, but was never PATCH-able from the Admin API and never surfaced anywhere in the Admin UI, meaning a flagged row (from this round's import, or any earlier one) had no visible "needs attention" signal and no way to be cleared once checked. `app/api/admin/parameters/route.ts`'s PATCH whitelist now includes it; the Parameters table shows a dismissible "N parameters need review" banner and a per-row `NEEDS REVIEW` pill; the edit drawer (`ParamEditForm`) shows an explanatory notice and a "confirmed against the source document" checkbox that clears the flag on save. This is the piece of the UI/UX instruction most directly earned by this round's own data import (20 rows land here on day one), but it applies to every module's flagged parameters, not only Quality's.

**Judgment call: what "for all the modules" does not mean here.** Solvent's and Finance's own entry/dashboard screens were left exactly as they are — this round's PDFs are Quality-only source documents, there is no new Solvent or Finance data driving a UI change, and touching those screens without a driving data change would be scope creep against both the explicit "modify the code only for the existing QC data entry" instruction and the hard Finance-logic boundary. "All the modules" is read here as: every screen where this round's Quality realignment surfaces (entry, dashboard, analytics, and the Admin config that governs Quality parameters, which is genuinely shared code with Solvent/Boiler) — not a license to open unrelated modules.
