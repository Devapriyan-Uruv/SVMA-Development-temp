# UI Redesign Notes

## Starting point — read this first

The ZIP you supplied (`SVMA_AI_Intelligence_Platform_V2_5_PREMIUM_UX_FINAL`) was **already** a mature "premium" pass: a dark-navy sidebar, restrained shadow/radius/spacing tokens, a source-accurate sticky-header entry table, gradient hero banners, and a split-screen login. It is not a generic template or an unstyled scaffold. This document describes the delta applied on top of that baseline to push it toward the flatter, more restrained "CRM Dashboard for SaaS Platform" reference brief (neutral background, dark navy nav, white surfaces, subtle borders, restrained shadows, drawers/modals instead of always-open forms) — it does not re-describe work that was already done.

This pass went through four rounds, plus a fifth (V3) that was backend-only and is documented in `IMPLEMENTATION_NOTES.md` rather than here, and now a sixth (V4, immediately below). Round 1 (section-by-section notes below) restyled surfaces and added the missing design-system primitives, but kept the app's original, very small type scale (many labels were 8–13px) — which is why it still read as "the same" visually. Round 2 actually opens the Behance reference, then rescales typography, spacing and corner radius across the whole app to match its character. Round 3 rebuilds the color and list-row system around the "SaaSto" SaaS template you supplied as a Figma export. Round 4 is not a visual round at all: it fixes a real reliability bug you hit while doing live data entry, and turns on live deviation notifications to the CEO and Solvent Head.

## Round 6 — V4 Quality entry grid, dashboard rollups, and Admin review flagging

You supplied three new PDF lab-report forms (one per product — PK, COPRA, RB) and asked for the code to be scoped strictly to the existing QC data entry, with the UI redesigned "like a UI/UX developer for all the modules." The data-side re-derivation is in `QUALITY_MAPPING.md` §8 and `IMPLEMENTATION_NOTES.md` §6; this section is the UI/UX side of that same round.

**1. The Quality hourly entry screen now mirrors the paper form it replaces.** Every prior round's entry table (`.source-entry-table`, still used unchanged by Solvent) shows one hour at a time — you pick an hour from the rail, fill that column, save, move on. The three attached PDFs make clear that's not how a Quality technician actually thinks about a shift: the paper form itself is laid out as one row per parameter with all 8 hour columns side by side, plus trailing MIN/MAX/AVG columns computed by eye across the row. The new `QualityGridTable` (inside `components/ParameterEntryBoard.tsx`, active only when `scope==='quality'&&actualMode==='hourly'` — Solvent's table is untouched) reproduces that layout on screen: every hour column visible per parameter row at once, the currently-selected hour highlighted and the only one that's actually editable (typing in a different hour's cell jumps the active-hour selector there instead of editing in place), a locked read-only value with a status-colored tone (green/amber/red/purple for normal/warning/critical/target-missing) for every hour already submitted, a "—" placeholder for hours not yet due, and "·" for a parameter that isn't scheduled that hour at all (e.g. a 4-hourly reading in an hourly-column grid). This is a rendering and information-density change only — deliberately, so none of the operational-integrity guarantees from the V3 round change: the save button still submits only the currently-due hour's row (`dueRows`, separated from the full `currentRows` the grid renders, specifically so the grid's full visibility can't accidentally submit a non-due parameter), a locked cell is still genuinely locked (same immutability trigger, same 409 ENTRY_LOCKED, same amendment-only correction path), and nothing about how a reading is validated changed.

**2. MIN/MAX join the existing AVG, computed the same way.** The paper form's trailing rollup columns are now on screen too — not just in the new entry grid (computed client-side from the shift's already-loaded `entries`, the same data the grid already renders) but on the Quality dashboard and analytics pages, where `app/api/quality/dashboard/route.ts` now computes `min`/`max` with `Math.min`/`Math.max` right alongside the `average` it already computed, over the same per-parameter numeric-reading array. Deliberately **not** a new stored column — pure arithmetic over readings that already exist, so it's always exact and can never drift out of sync with the underlying entries the way a cached/stored rollup could.

**3. A real, pre-existing gap in Admin → Parameters, closed as part of "redesign the UI for all the modules."** While wiring up this round's 20 newly-flagged rows (see `QUALITY_MAPPING.md` §8), a grep turned up that `parameter_master.source_review_required` — a column that has existed since `001_schema.sql`, in the very first round of this project — was never in the Admin API's PATCH whitelist and never rendered anywhere in the Admin UI. Practically: a parameter flagged for human review had no visible signal in Admin and no way to ever be un-flagged short of a direct database edit. That's now fixed, for every module's flagged parameters, not only Quality's freshly-imported ones: a dismissible amber banner above the Parameters table ("N parameters need review — imported from a source document with a target that could not be parsed without guessing"), a per-row `NEEDS REVIEW` pill next to the parameter's name, and — inside the edit drawer itself — an explanatory notice plus a "confirmed against the source document" checkbox that clears the flag when the parameter is saved. All additive CSS in a new "V8" layer at the end of `app/globals.css`; nothing from V1–V7 was touched.

**What this round deliberately did not restyle.** Per your own scoping instruction ("modify the code only for the existing QC data entry"), Solvent's and Finance's entry/dashboard/analytics screens were left exactly as rounds 1–4 left them — there's no new Solvent or Finance source document driving a UI change this round, and the four prior rounds already gave the whole app (Solvent and Finance included) the typography, spacing, color and component-system pass described below. "For all the modules" is read here as: every screen the Quality realignment itself touches, including the Admin parameter-review flow that's genuinely shared across modules — not a re-run of the full-app visual redesign on data that didn't change.

## Round 4 — data-entry reliability fix + live deviation notifications

You reported that while entering a day's readings, a save "automatically threw me out" and you then couldn't log back in. Your own terminal log (pasted in the request) was the key evidence — here's what it shows and what was actually fixed.

**What the log actually shows.** Every `POST /api/entries` call in your log returned `200` — every reading you entered was saved successfully before anything went wrong. The failure was a separate, later request: `POST /api/reports 500 in 43s`. That route generates the AI narrative summary (the "what went well / needs attention" panel) and is called automatically after every save. Two bugs in that flow, both now fixed:

1. **The Save button was waiting on the AI call, not just the save.** `components/ParameterEntryBoard.tsx` had `await ai(true)` inside the save function — so after your readings were already safely written, the UI stayed in its "saving" state for however long the AI call took (in your log, 43 seconds, then it failed). That's exactly what a hang looks like, right after data that had, in fact, already been saved. Fixed: the AI summary refresh is now fired in the background (`void ai(true)`) and no longer blocks the save confirmation — Save now completes and shows "N entries saved" the moment your readings are actually written, typically well under a second, regardless of how long the AI narrative takes.
2. **A slow/failing AI call was discarding an already-computed, perfectly good report.** `app/api/reports/route.ts` computes a deterministic report first (target validation, deviation counts — no AI involved) and only then asks OpenAI for narrative commentary on top of it. If that OpenAI call was slow or errored, the whole request — including the deterministic part that had already succeeded — failed with a 500, which is the exact error in your log. Fixed: the OpenAI call is now wrapped in its own try/catch with a 20-second cap, and on any failure it falls back to the deterministic report (with a note that AI commentary wasn't available) instead of failing the request. **Nothing about how a deviation is detected, what counts as a target breach, or what the deterministic report contains was changed** — only what happens when the optional AI narration on top of it is slow or unreachable.

**About being unable to log back in:** your log shows `POST /api/auth/login 401` a few times in a row — that status code means Supabase rejected the email/password combination itself (it comes straight back from `supabase.auth.signInWithPassword`, before this app's own code runs). That's not something fixable from this codebase; if it keeps happening, check the exact error text shown on the login page itself (it'll say e.g. "Invalid login credentials"), and if the password is definitely right, check that account's status in the Supabase Auth dashboard. Separately: your earlier session very likely simply expired (Supabase access tokens are time-limited by default) — that's a normal, expected event on a long shift, and is unrelated to bug #1/#2 above, though the 43-second stall made it feel connected. **Nothing you entered was lost** — it was already saved before any of this happened.

**Live deviation notifications for CEO / Solvent Head.** The action you asked for — alert the CEO and Solvent Head the moment a saved entry raises a deviation — turned out to already be half-built: `app/api/entries/route.ts` (untouched by this round) already writes a row to the `notifications` table for exactly the right people every time a saved reading is outside target (Solvent deviations notify `solvent_head`, Quality deviations notify `quality_head`, and both always include `ceo`/`management`/`admin`/`super_admin`) — this is deterministic, not AI-decided, and was already correct. What was missing was a way to see it: the topbar bell (added in round 1) was a static icon with nothing behind it. Now built:
- `app/api/notifications/route.ts` (new) — `GET` returns the signed-in user's own notifications and unread count; `PATCH` marks one or all as read. Every query is explicitly scoped to `user_id = the signed-in user`, the same pattern already used elsewhere in this codebase (`app/api/reports`, `app/api/entries`) for privileged reads.
- `components/NotificationBell.tsx` (new) — the bell now shows a live unread-count badge, polls every 45 seconds, and opens a dropdown of recent alerts (severity dot, title, detail, relative time). Clicking one marks it read and opens the relevant Action Ticket board (Solvent or Quality).
- `components/AppShell.tsx` — swapped the static bell button for `<NotificationBell/>`; nothing else in the shell changed.

No SQL migration is needed — the `notifications` table and its row-level-security policy already existed in `sql/001_schema.sql` (untouched).

## Round 3 — SaaSto reference: colorful icon system + human list rows

You uploaded a Figma export of a SaaS marketing/app template ("SaaSto") and asked for a redesign that uses its components as a base, without changing the app's concept or logic, because the result still looked AI-generated. That template's screens (three home-page hero variants plus a finance-app mobile mockup) were opened and inspected directly. Three concrete patterns were carried over — rebuilt from scratch with SVMA's own icons, copy and data, nothing from the template's own artwork reused:

1. **Colorful, purposeful icon chips instead of one repeated blue.** The template's "Recent Category" row uses a different pastel color per icon (blue, pink, lavender, sky). This codebase already had a `tone-*` class system on the Home workspace cards (`tone-blue`, `tone-green`, `tone-purple`, …) but the icon chip inside each card ignored it and was always the same light-blue square. That's now fixed — `.workspace-icon` picks up its card's own tone, so Solvent, Quality, Finance, Admin etc. each get a distinct, consistent accent color instead of a uniform "AI dashboard blue."
2. **The same tone system extended to every KPI stat card.** `components/Kpi.tsx` gained two new *optional* props, `icon` and `tone` (existing calls with neither prop still render exactly as before — nothing about the KPI data or its call signature is required to change). All 14 KPI call-sites across Solvent, Quality, CEO Cockpit, Finance and the two Analytics pages now pass a meaningful icon and color: health/coverage in blue or green, quality in purple, warnings in amber, open actions/critical items in rose. This mirrors the template's colored stat cards and gives each number a visual "meaning" instead of a wall of identical navy digits.
3. **Avatar/icon list rows instead of dense data-grid tables**, matching the template's "Transactions" list (a colored circular icon, a two-line title/subtitle, right-aligned meta, a status chip). Applied to the two places where it reads most naturally as "a list of things happening," not "a spreadsheet": the Action Ticket list (`components/TicketBoard.tsx` — Solvent and Quality both use it) and the Admin Users tab (`app/admin/page.tsx`). Both keep the exact same data, endpoints and click handlers as before (open a ticket in its drawer, edit/disable a user) — only the row markup changed, from `<table><tr>` to a `.row-list` of cards with a colored avatar/icon on the left.

Everything above is additive CSS (a new "V5" section at the end of `app/globals.css`) plus small, backward-compatible prop additions and row-markup swaps in three files (`components/Kpi.tsx`, `components/TicketBoard.tsx`, `app/admin/page.tsx`) and one small helper export (`components/StatusBadge.tsx` now also exports `statusTone()` so the ticket list can color its icon by the same status logic the badge already used). No data-fetching call, endpoint, payload shape, or piece of Finance/Solvent/Quality business logic changed — see `FINANCE_LOGIC_VERIFICATION.md` for the re-verified hash check. The Admin Parameters and Shifts tabs, and every other data table in the app, were deliberately left as tables — they're genuinely spreadsheet-like (many numeric/technical columns), where a table is the correct, scannable format; converting those to card rows would hurt usability rather than help it.

## Round 2 — actually viewing the Behance reference, and what it changed

Round 1 shipped with a note saying the Behance page couldn't be opened in this environment. That was true when written, but **it was worked around in this round**: the built-in browser was used to open the case study directly (behance.net/gallery/241565381) and its individual project-module frames, so the redesign below is based on what the reference actually looks like, not a generic "premium SaaS" guess. Nothing was traced, screenshotted-and-reused, or copied — no image, icon, illustration, logo, or line of copy from the reference is in this codebase; only the *characteristics* below were carried over and re-implemented from scratch against SVMA's own content:

- **Typeface** — the reference uses **Urbanist**, a rounded-geometric sans with noticeably bigger, bolder headings than a typical dense admin panel. `app/layout.tsx` now self-hosts Urbanist as a variable font (`app/fonts/Urbanist-Variable.ttf`, OFL-licensed, bundled locally) via `next/font/local` and exposes it as `--font-display`; `app/globals.css` now sets it as the app's font-family. It's self-hosted rather than fetched from Google Fonts at build time so `next build` never depends on reaching `fonts.googleapis.com` — that network call is blocked in this environment's sandbox and can't be assumed to work in every build environment.
- **Type scale** — the reference's body text, labels and headings all run noticeably larger and bolder than this codebase's original scale (which had dozens of 8–13px classes). Every base-level `font-size` rule in `app/globals.css` was parsed programmatically (cascade-correct — computed from the last-applied value per selector, ignoring `@media` overrides) and rescaled with a tiered multiplier so small text grows proportionally more than large text (e.g. an 8px pill label becomes ~12.5px; a 28px page title becomes ~32.5px). 218 selectors were rescaled this way — see the "V4" section at the end of `app/globals.css`.
- **Corner radius & spacing** — the reference's cards, buttons and inputs are noticeably more rounded and airier than the original scale. `--radius-sm/md/lg/xl` were increased (10→12, 16→20, 22→28, 28→34px) and padding was opened up on cards, KPI cards, buttons, form fields, table cells, nav items and the login card.

All of this is additive CSS layered at the very end of `app/globals.css` (plus the one font import in `app/layout.tsx`) — no component markup, data-fetching, or business logic changed in this round, and no Finance file was touched (re-verified — see `FINANCE_LOGIC_VERIFICATION.md`).

## Round 1 — what changed, and why

### 1. Flattened the gradient "hero" blocks (biggest single visual change)
Your brief explicitly asked to avoid "random gradients" and "excessive blue." Every full-bleed navy gradient banner (`.intelligence-hero`, `.hero`, `.module-hero`, `.finance-hero`, `.welcome-strip`, `.compact-hero`, `.live-context`, `.admin-banner`, etc. — nine class families in total) was flattened to a white/neutral card with a slim 2-color accent bar and no decorative radial "glow" circles. This is a pure CSS override layered at the end of `app/globals.css`, so it applies uniformly across CEO Cockpit, Solvent, Quality, Finance, Admin and the shift-start screens without needing to touch each page's markup. The one deliberate exception is the login page's left panel, which keeps a single flat navy fill (a standard split-screen SaaS auth pattern) — the decorative rings were removed from it too.

### 2. Added the missing design-system primitives
The codebase had cards, buttons, pills, tables and tabs, but no **Drawer**, **Modal**, **Skeleton**, or **EmptyState** components existed anywhere (confirmed by search — zero matches). These are now real, reusable components:
- `components/Drawer.tsx` — slide-over panel (Esc to close, backdrop click to close, scroll-locked body).
- `components/Modal.tsx` — centered confirmation dialog (info/danger tone).
- `components/Skeleton.tsx` — `SkeletonLine`, `SkeletonKpis`, `SkeletonCard`, `SkeletonTable`, `SkeletonDashboard`.
- `components/EmptyState.tsx`, `components/AlertBanner.tsx`, `components/FilterBar.tsx`, `components/StatusBadge.tsx`, `components/SegmentedControl.tsx`.

### 3. Administration — drawers instead of giant inline forms
This was the clearest gap against your brief ("Avoid giant inline forms" / "side drawers for Create/Edit" / "searchable data table"). Previously the Users, Parameters and Shifts tabs each showed a full create form permanently expanded at the top of the page, and the Parameters tab rendered a 19-column, always-editable input in every table cell for every row. `app/admin/page.tsx` was restructured so that:
- Each tab has a compact, searchable, read-only table plus a **+ Add** button that opens a Drawer with the create form.
- Each row has an **Edit** button that opens a Drawer with that row's fields.
- Disabling a user now goes through a confirmation **Modal** (destructive-action confirmation, per your interaction-polish requirement).
- All fetch/POST/PATCH calls, payload field names, and the `roleDefaults`/module list are byte-identical to the original — only the JSX around them changed.

### 4. Ticket workflow — detail drawer
Section 12 asked for a "ticket detail drawer." The Solvent and Quality ticket pages were near-identical ~1-line-per-file copies of a long always-expanded card per ticket. They're now a single shared `components/TicketBoard.tsx` (parameterised by `scope`) that renders a compact table and opens the full acknowledge/investigate/evidence/close workflow in a Drawer. Same `/api/tickets` and `/api/tickets/evidence` endpoints, same request bodies, same status machine.

### 5. Skeleton loading states
Home, Solvent Overview and Quality Overview previously rendered nothing (a blank content area) until their `fetch` resolved. They now show a `SkeletonDashboard`/`SkeletonKpis` placeholder during that window. No data-fetching logic changed — this is strictly an added branch that renders before the existing render path.

### 6. Sidebar navigation grouping + notifications affordance
`components/AppShell.tsx` now groups the nav into labelled sections (Workspace / Intelligence / Data Capture / System) instead of one flat list, and a notifications bell icon was added to the top bar chrome. The bell is currently a static affordance (no backend notification feed exists in this codebase) rather than wired to fabricated counts — wiring it to a real feed is a good next step once there's a notifications table/endpoint to back it.

### 7. Finance
**Zero Finance `.tsx`/`.ts` files were opened for writing.** Finance pages (`app/finance/**`) pick up the flattened-hero treatment, the button/card/table refinements, and the focus-visible states purely because they use the same shared CSS classes and the same `PageHeader`/`Kpi` components — which is the safest possible way to restyle Finance without any risk to its logic. See `FINANCE_LOGIC_VERIFICATION.md` for the hash proof.

## What was intentionally left as-is

Given the size of the brief (25 numbered sections covering essentially every screen in the product), this pass prioritized: (a) the items that were factually missing (Drawer/Modal/Skeleton, grouped nav, searchable admin tables), (b) the single highest-leverage visual change (de-gradient-ing the hero surfaces, which touches every module at once), and (c) doing all of it without so much as opening a Finance logic file. The following were **not** rebuilt in this pass, because the existing implementation already substantially matches the brief and a rewrite would have added risk without a clear visual payoff:
- Analytics charts (`app/solvent/analytics`, `app/quality/analytics`) — already implement target-band trend lines, product/shift filters and compliance bars; they inherit the flattened surfaces automatically but their chart internals (`components/IntelligenceCharts.tsx`) were not rewritten.
- The hourly/shift data-entry table (`components/ParameterEntryBoard.tsx`) — already implements the sticky S.No/Parameter columns, hour selector, category tabs, product tabs, offline queueing and Normal/Warning/Critical legend called for in sections 7–9; it was left alone since it already satisfies "do not rearrange the source categories."
- Reports pages, Deviation registers, and the AI-inference pages — already use the card/table system and inherit the CSS refinement; not individually rewritten.

If you'd like a second pass focused specifically on any of the above (e.g., rebuilding the analytics charts as a proper charting component, or wiring a real notifications feed), that's a clean, scoped follow-up.
